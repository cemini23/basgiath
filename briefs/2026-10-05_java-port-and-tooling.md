# Basgiath — improvement, editing ergonomics, and the Java port path

**Date:** 2026-10-05 · **Home:** `Projects/dragon-rider-map/briefs/`
**Wiki context:** Game Dev wiki `concepts/minecraft-modding-ecosystem.md`, `concepts/minecraft-bedrock-addons-scripting.md`, `concepts/minecraft-data-driven-content-patterns.md`, `entities/tools/blockbench.md`

## The one thing that makes the port cheap

Basgiath does not ship a hand-built world. `scripts/build_map.py` writes `.mcfunction` files, and `/function basgiath/build` raises the college at runtime. The dragon is generated by `build_dragon_model.py`. The script is one file, `main.js`.

That means a Java port is **a code port, not a world conversion.** Bedrock worlds are LevelDB and Java worlds are Anvil; `.mcworld` cannot be imported. But nothing here needs importing — the world is regenerated from source every time. Port the generator, the script, and the entity, and the map reappears on Java.

Three artifacts move. Everything else follows.

| Artifact | Effort | Why |
|----------|--------|-----|
| `scripts/zones/*` → Java function emitter | Medium | Command syntax differs; the generator structure is reusable |
| `scripts/build_dragon_model.py` | Medium | Bedrock geometry, not Java model JSON — a real rewrite |
| `addon/behavior_pack/scripts/main.js` | Medium | Bedrock Script API → Java mod events |

## Part 1 — Improve Basgiath on Bedrock

### Script API — facts worth pinning

- `@minecraft/server` stable is **backward-compatible within a major line**; a dependency on `2.0.0` is satisfied by later `2.x`. The pinned `2.0.0` in both manifests is the right call. [CONFIRMED]
- Stable takes a **major bump roughly once per Minecraft minor release** — `1.11.0` at 1.21.0, `1.17.0` at 1.21.60, `2.5.0` at 1.26.0. Expect a migration task at the next bump. Budget for it. [CONFIRMED]
- No `setTimeout` / `setInterval`. Use `system.runTimeout` and `system.runInterval`. One-tick precision. [CONFIRMED]
- `script_eval` capability enables `eval()`. If `main.js` never uses it, leave the capability out.
- `server-admin` and `server-net` are **Bedrock Dedicated Server only**. Do not design anything that needs them for the free MCPEDL/CurseForge distribution.

### The test bench (from K281, still the highest-leverage item)

K281 proposed `bedrock-mc/mcpelauncher-agent` + `itzg/docker-minecraft-server` + `dadeeen/MCBE_Inventory_Editor`. Start with the container pair: it gives headless world-gen and pack-load validation with no agent and no client automation. That removes most manual clicking before any UI automation is written.

## Part 2 — Porting to Java

### Pick the target first

**Loader.** NeoForge is the promoted successor to Forge and the feature-rich lane; Fabric is lighter and loads faster. For a map that needs a custom entity, custom blocks, and events, **NeoForge** is the better fit. Use Architectury only if Bedrock and Java must share source, which they cannot.

**Version.** Pick one target and sit on it. Java mods break per release, and the community's habit is to hold a stable "LTS" version rather than chase drops.

### The deobfuscation change — this is good news

Mojang dropped obfuscation in Java after 1.21.11. Consequences: [CONFIRMED — fabricmc.net, 2025-10-31]

- The game ships **official Mojang names at runtime**.
- **Yarn is deprecated** and **Intermediary ceases to exist**. Do not start a new project on Yarn.
- Method parameter and local variable names are now visible.
- **New mods should use official Mojang mappings.**

Practical effect: a Java port started today is easier than at any prior point in Minecraft's history. The cost is that **no mod compiled for 1.21.11 or earlier works on 26.1 without recompilation** — so do not expect an existing mod to be a starting template without a port pass.

### Toolchain

| Need | Tool |
|------|------|
| NeoForge Gradle plugin | **ModDevGradle** (`neoforged/ModDevGradle`) |
| Project scaffold | NeoForge web Mod Generator |
| IDE support | **MinecraftDev** IntelliJ plugin (LGPL-3.0) — Mixin, setup for all loaders |
| Mappings | **Mojmap** (official). Parchment is now optional since Mojang ships parameter names |
| Animation | **GeckoLib** — the standard for Bedrock-style animated entities on Java |
| Publishing | Minotaur Gradle plugin (Modrinth) or `mc-publish` GitHub Action |

### The mapping table — what goes where

| Basgiath today | Java equivalent | Difficulty |
|----------------|-----------------|------------|
| `functions/basgiath/*.mcfunction` | Datapack functions — **the same concept, different command syntax** | Medium |
| `main.js` (`@minecraft/server` 2.0.0) | NeoForge event handlers + commands | Medium |
| `main.js` forms (`@minecraft/server-ui`) | A custom `Screen`, or **dialogs** (1.21.6+), or a written book | Medium |
| Player dynamic property (signet result) | NeoForge **data attachments** or a capability | Low |
| World dynamic property (wing roster) | **`SavedData`** | Low |
| `#bond map_state` scoreboard | Java scoreboard — **identical concept** | Low |
| Bedrock dragon geometry + animations | Java entity model JSON **+ GeckoLib** (different formats) | **High** |
| `build_dragon_model.py` | Rewrite to emit Java model JSON | **High** |
| Bedrock structure blocks / world template | Java **jigsaw** + structure NBT, or keep generating from functions | Medium |
| `/function basgiath/build` | Same pattern — a datapack function | Low |

The two High rows are the real work. Everything else is mechanical.

### What the port unlocks

The declared scope cuts stop being necessary on Java:

- **Custom dimension** — cut on Bedrock because Bedrock custom dimensions are experimental and void-only. Java has real custom dimensions. A dedicated Basgiath dimension becomes possible.
- **Custom block art** — cut on Bedrock. Java supports custom blocks with textures. The college need not stay vanilla-only.
- **Custom shaders and fonts** — Bedrock cannot. Java can.
- **Arbitrary code** — the Script API is a sandbox; Java is not. Flight physics, custom AI, and inventory systems stop being constrained by what `@minecraft/server` exposes.

### What the port costs

- **The audience.** Bedrock is roughly 78% of players by fan estimate and is where phones, tablets, and consoles live. Java is PC-only. The README already names this as the reason for choosing Bedrock. The port is additive only if the Bedrock release continues in parallel.
- **The model rewrite.** The dragon is the expensive part, on both sides.
- **A second maintenance surface.** Two editions means two version-churn calendars.

### Do the port as a parallel track, not a migration

The cheapest shape is: keep Bedrock shipping to MCPEDL and CurseForge, and port to Java as a second target sharing the same generator source. `build_map.py` emitting both Bedrock and Java functions is a smaller change than maintaining two generators.

## What not to do

- Do not enable Beta APIs to get a feature. Stable is enough and Beta breaks at any increment.
- Do not start a Java port on Yarn. It is deprecated.
- Do not expect `.mcworld` to import into Java. It cannot. Regenerate instead.
- Do not run the full three-part test bench before the container pair proves itself.
- No client-modification code, no anticheat evasion, no hacked clients. This is a non-monetized fan project and that boundary is unchanged on either edition.

## Open question for the operator

Does the Java port ship publicly, or is it a capability experiment? The answer decides how much effort goes into the dragon model rewrite, which is the only genuinely expensive task here.
