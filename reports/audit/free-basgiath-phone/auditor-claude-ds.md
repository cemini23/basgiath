### Root cause (if debugging)
The design assumes `/schedule` will run `raise`/`fill_far` in a context where `execute as @e[type=armor_stand,name="build_anchor",c=1] at @s` resolves and the far chunks are loaded. On this phone, `schedule` runs as the server at world spawn; the anchor may not be matched (or the ticking areas failed to register because four radius-4 circles exceed the ~100-chunk/area limit), so the far files either no-op or run with wrong tilde origins. The near inline pass also cannot place far blocks because those chunks are unloaded at build time. Result: east stairs and plaza never appear, matching the "gate with no stairs" symptom. The smallest fix is to remove the `schedule` calls and place far blocks from the `build` body itself, after adding correctly-sized ticking areas, using `execute as @e[...build_anchor...] at @s run function basgiath/far_XX` directly — and to shrink the ticking areas to radius 2–3 so they actually register.

### Confidence
medium — the `schedule`-as-server and ticking-area-size issues are well-documented Bedrock behaviors and match the reported symptoms, but I cannot see the actual `far_02..11` contents or confirm whether the anchor entity survives the scheduled delay on this phone. Would change my mind if a playtest showed the far pass running correctly with the current `schedule` calls, or if `tickingarea add circle ... 4` is confirmed to succeed on this device.

### Unique angle
Other models may focus on the `tick.json`/`main.js` tick loop or the stage count, but the real killer is that `schedule` executes as the server at world spawn — so even though `raise.mcfunction` *looks* anchor-relative, the scheduled invocation's outer context is wrong, and the four radius-4 ticking areas likely exceed the per-area chunk limit, silently failing to load the far chunks. The fix is not "wait longer" but "place far blocks from the build body with smaller ticking areas."
