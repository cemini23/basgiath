**Root cause**  
The generator emits Bedrock commands as the source of truth. `editions.py` translates them to Java, but the translation is a *post-process* that cannot feed back into the Bedrock path. This creates three classes of drift: (1) commands that translate syntactically but shift semantics (relative selectors hoisted incorrectly when an explicit `positioned` already exists), (2) edition-specific mechanics dropped without replacement (tickingarea/schedule on_area_loaded → far chunks never load on Java), and (3) runtime differences the translator cannot express (action bar via chat overlay vs native, real-time vs tick-based timeouts). The Bedrock output is frozen (git diff clean), so every Java divergence is a one-way ratchet.

**Confidence**  
High. Every finding above is traceable to a specific line in the provided files. The selector hoisting bug (live.mcfunction line 3) is mechanically verifiable by comparing the two generated files. The missing far-fill schedule is visible in the Java `raise.mcfunction` vs Bedrock's `schedule on_area_loaded`. The action bar implementation difference is in the source code of `FlightHud.java` vs `main.js`.

**Unique angle**  
The translator's `_hoist_in_chain` treats `positioned` as a pure prefix insertion, but Bedrock commands *already* use `positioned` for macro-positioning (e.g., the wind push at `~15 ~33 ~19`) while *also* using relative selectors for micro-positioning (the `dx=63,dy=2,dz=2` box at `x=~4,y=~32,z=~14`). The two offsets are *composed* in Bedrock (the selector measures from the positioned location). The translator hoists the selector's offset *without removing the original `positioned`*, so Java gets two `positioned` in sequence — the second wins, shifting the selection box by 11 blocks east, 1 block up, 5 blocks south. This is the only bug that requires reading *both* generated files side-by-side; a single-edition review sees valid syntax in each.
