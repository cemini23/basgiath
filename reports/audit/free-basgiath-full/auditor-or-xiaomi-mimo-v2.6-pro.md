### Root cause
The Phase 4 fix correctly identified that the far retry is the only place a command lands for an unloaded chunk, but it scoped that insight to block placement only. `_box()`/`is_far()` were written as a fill/setblock parser, and every gate (`far_air >= 100`, "far retry missed the east stairs", "far retry missed the lodestone", `bench_static.phone_lines`) is built on the same parser. A command class the parser does not understand is invisible to the whole verification stack, so the retry silently omits it and every test stays green. The `summon` commands are exactly that class, and all four of them are outside the loaded box.

### Confidence
**medium-high** on the `summon` gap — the coordinates and the filter logic are unambiguous from the emitted code. What would raise it to high: confirming that Bedrock's `summon` with explicit coordinates in an unloaded chunk is a silent no-op (I believe it is, but no client was run, per the brief). What would lower it: if the `tickingarea add … true` preload in `build_text` guarantees those chunks are loaded before the stage calls execute in the same tick — the code adds the areas before the stage calls, but chunk loading is not synchronous with the command stream.

### Unique angle
The verification stack has a shared blind spot rather than a bug: `build_map.is_far`, `bench_static.is_far`, and `bench_static.phone_lines` all derive "what the phone runs" from the same `_box` parser, so the checker and the generator fail in the same direction. The `prove()` mutations in `bench_static` only exercise block edits, so the suite can prove it rejects a deleted span but cannot prove it would reject a dropped spawn. A second, quieter instance of the same shape: `test_release` asserts `"function basgiath/stage_20"` exists in `build.mcfunction`, which is a hard-coded stage count that will break the moment a zone grows past 32 stages — a gate that encodes a number the generator chooses.
