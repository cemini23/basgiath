### Root cause (if debugging)
The bench is a *simulator* of Bedrock's `setblock`/`fill` semantics, not an observer of the real game. It correctly replays the shipped `stage_*.mcfunction` files and would fail if `parapet()` were deleted from `build_map.py` — but only because `build_map.py` itself would fail first via its own `assert_walk`. The bench's "proof" mutations are tautological: they append commands that directly contradict the assertion, then re-run the same checker. The real gap is that no automated check observes the *shipped `.mcworld`* containing the college blocks (the bench explicitly notes this), and the BDS smoke test that *would* observe the real runtime is not in CI and was not run. To close the gap, inspect whether `bench_bds.sh`'s coordinates (`20 112 20`) are a stale origin or a different coordinate system, and add a CI job that runs the BDS script on a Linux runner.

### Confidence
medium — I am confident the bench catches a deleted Parapet via the function replay, and confident the BDS script is not in CI. I am less confident about the `stone_pressure_plate` solidity assumption and whether `bench_bds.sh`'s coordinates are stale or intentional; inspecting a real Bedrock block list and the BDS script's git history would change my mind.

### Unique angle
The bench's `assert_world` comment is the tell: it *knows* the `.mcworld` does not contain the college, so it deliberately avoids counting blocks there. This means the only automated check that the Parapet exists in a *shipped artifact* is the function-file replay — and that replay reads the same files `build_map.py` writes, so a bug in `build_map.py` that produces syntactically valid but semantically wrong commands (e.g. wrong z) would pass both `build_map.py`'s `assert_walk` and `bench_static.py`'s `assert_parapet` if the wrong z is consistent. The bench is not decoration, but it is a *consistency* check, not a *correctness* check against the game.
