| High | Selector `c=` argument not converted to `limit=` when first in selector, causing Java parse failure | scripts/editions.py:174 (in `_java_selectors` function, line containing `body = re.sub(r"(?<=[,\[])c=(\d+)", r"limit=\1", match.group(0))`) | Modify regex to allow start of selector: `r"(?<=[,\[]|^)c=(\d+)"` or use word-boundary approach |

**Root cause:** The regex for converting Bedrock's `c=N` to Java's `limit=N` requires a preceding comma or open bracket (`(?<=[,\[])`). When `c=` is the first argument in a selector (e.g., `@e[c=1,type=armor_stand]`), there is no preceding comma/bracket, so the conversion fails. The selector retains invalid `c=` syntax, causing the function to fail to load at startup in Java 1.21.1 (silent failure during build if missed, but actually a loud parse error—however, the build would stop due to `TranslationError` only if the command is untranslatable; here it translates incorrectly to invalid Java syntax, which the build doesn't validate until runtime). This mirrors the relative coordinate issue: both cause function load failure due to untranslated selector syntax.

**Confidence:** High. The regex is inspectable and the logic flaw is clear. A test case like `to_java('execute at @s run tag @e[c=1] add x')` would output `execute at @s run tag @e[c=1] add x` (invalid Java), confirming the issue. Changed mind if the generator never places `c=` first—but the Bedrock-to-Java translation must handle all valid Bedrock selector orders.

**Unique angle:** Only the `c=` position vulnerability is missed; the existing tests cover `c=` after commas (see `test_editions.py`) but not leading `c=`. This is the "seam" where Bedrock's flexible selector argument order leaks into Java's stricter expectations.
