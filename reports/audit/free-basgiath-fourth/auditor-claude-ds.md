### Root cause
The generator emits anchor-relative commands, and the script API sees absolute world positions. The keeper fix resolved the anchor in `buildOrigin()` and compared `Math.floor(anchor) + relative`. The same shape survives in `live_lines()`: the valley bond trigger and the gauntlet rope boxes use `~` offsets that are relative to the anchor, not absolute world coordinates. The script does not read those boxes — they are pure command selectors — so the mismatch is invisible to the script and to the static bench, which replays commands at the origin. The generator and its checkers share the same parser, so a class the parser does not understand (a selector box with `~` offsets) is invisible to both. This is the same root cause as audits 1–3, now in the live tick rather than the build pass.

### Confidence
medium — the keeper fix is verified by `bench_static.py`'s off-origin proof, and the lectern coordinates match the generator. The live-line mismatch is real but its impact depends on whether the map is ever built off-origin; the README says "stand on open ground and run the same function," which implies off-origin builds are supported. What would change my mind: a `test_release.py` check that parses the `live_lines()` selectors and asserts they resolve to the dell/gauntlet boxes at an off-origin anchor, or a statement that the map is only valid at the origin.

### Unique angle
The `bench_static.py` keeper proof is the strongest guard in the repo, but it only covers the two keepers. The valley bond trigger and the gauntlet rope boxes are the same class of bug and have no equivalent proof. A future audit should extend `prove_keeper_origin` to drive the live-line selectors against an off-origin anchor, or add a static check that the `~` offsets in `live_lines()` match the absolute zone coordinates.
