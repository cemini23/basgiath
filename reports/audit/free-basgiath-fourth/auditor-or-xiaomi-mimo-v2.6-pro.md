### Verdict
WARN — the origin class is now consistent everywhere I can reach, but two script-side defects remain (unhandled form rejection on disconnect/busy, and a roll-call tag that a second write inside the 60-tick beat can race), plus one shared blind spot in the checkers.

### Root cause
The origin class itself is closed: every anchor-relative command (`setblock ~128 ~1 ~34 lectern`, `zone-valley.py`'s `~50 ~-1 ~123`, the `live_lines()` selectors, `spawnpoint @p ~8 ~0 ~66`, `tp @p ~120 ~8 ~40`) is matched by a script or bench that adds the same floored anchor, and `bench_static.py`'s `prove_keeper_origin` drives the real handler against an off-origin anchor and a moved anchor. What remains is the *same shape of blind spot one level up*: the checkers read the keeper table out of `main.js` and the lectern positions out of the functions independently, so nothing proves the two agree. That is the third instance of "generator and checker share one source of truth, so a divergence is invisible to both."

### Confidence
medium — the origin arithmetic is high confidence (proved by the vm harness with a negative-coordinate anchor). The roll-call and form-lifecycle findings are read off `main.js` alone; I have not executed the script, so the exact Bedrock behaviour of `ModalFormData.show` on disconnect is `insufficient evidence` — inspect `@minecraft/server-ui` 2.0.0 docs for whether `show` rejects or returns `canceled: true` on a departed player.

### Unique angle
`test_release.py`'s `assert_lectern` scans the *whole* blob sorted by filename, so `far_*` sorts before `stage_*` and the "last emitted block" is taken from the stage pass — but the phone actually runs the far retry *after* the stage pass for those cells. If a future edit ever made the retry form differ (e.g. a `keep`-variant setblock), the assertion would read the wrong pass and stay green. The check should read the pass that actually lands last on a phone.
